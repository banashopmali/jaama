JAAMA — Landing Page Visual Implementation Contract

1. TON RÔLE

Tu agis comme le Senior Product Designer, Senior UI/UX Engineer et Senior Frontend Engineer officiel de JAAMA.

Tu travailles sur un produit SaaS africain de gestion d’entreprise nommé JAAMA.

Pour la Landing Page JAAMA, une image de référence officielle est fournie dans le projet.

Cette image constitue la VISUAL SOURCE OF TRUTH.

Ta mission n’est PAS de créer une landing page simplement inspirée de cette image.

Ta mission est de reproduire le plus fidèlement possible son rendu visuel, sa structure, ses proportions, sa hiérarchie et son identité, puis de l’implémenter proprement dans l’architecture frontend officielle de JAAMA.

⸻

2. RÈGLE ABSOLUE — VISUAL SOURCE OF TRUTH

Lorsqu’une image de référence JAAMA est fournie :

REFERENCE IMAGE > tes préférences personnelles > conventions génériques de templates SaaS.

Tu dois d’abord observer l’image, puis implémenter.

Tu ne dois jamais :

* remplacer la direction artistique par un template SaaS générique ;
* simplifier arbitrairement la composition ;
* modifier la hiérarchie visuelle sans nécessité technique ;
* changer les proportions parce qu’une autre disposition te paraît plus moderne ;
* réduire les tailles de texte ou de boutons ;
* supprimer des sections ;
* inventer de nouvelles sections ;
* transformer JAAMA en dashboard sombre ou landing page startup générique ;
* utiliser des gradients excessifs ;
* ajouter des animations décoratives inutiles ;
* modifier les textes métier sans instruction ;
* remplacer les visuels produit par des illustrations génériques si les assets officiels existent.

Si un détail exact n’est pas déterminable depuis la référence, reproduis l’intention visuelle la plus proche au lieu d’inventer un nouveau langage graphique.

5. TYPOGRAPHIE

La lisibilité est prioritaire.

JAAMA utilise volontairement :

* des titres importants ;
* une taille de texte confortable ;
* des boutons généreux ;
* une hiérarchie typographique très visible.

Ne réduis jamais artificiellement les polices pour faire rentrer davantage de contenu.

Hero H1

Le Hero doit comporter un titre extrêmement dominant :

« Gérez, vendez et développez votre entreprise. »

Le titre doit :

* occuper plusieurs lignes ;
* avoir un poids fort ;
* utiliser une couleur bleu marine presque noire ;
* présenter un line-height compact ;
* devenir immédiatement le premier point d’attention de la page.

Desktop indicatif :

* environ 58–72 px selon la largeur réellement disponible ;
* font-weight 700–800 ;
* letter-spacing légèrement négatif.

Les valeurs exactes doivent être ajustées visuellement par rapport à la référence.

Titres de sections

Utiliser une hiérarchie forte et cohérente.

Body

Texte confortable, jamais minuscule.

La lisibilité prime sur la quantité d’informations affichées.

19. RESPONSIVE DESIGN

La référence desktop constitue la source visuelle principale.

L’adaptation responsive doit préserver la même identité.

Desktop

Large container centré.

Largeur indicative :

max-width: 1280px à 1440px

selon la section.

Tablet

Réduire progressivement les colonnes et espacements sans casser la hiérarchie.

Mobile

Passer intelligemment en une colonne.

Ordre du Hero :

1. badge
2. H1
3. description
4. CTA
5. social proof
6. mockup produit

Les boutons principaux peuvent devenir full-width.

Les cards fonctionnalités passent en grille 1 ou 2 colonnes selon la largeur.

Pricing devient vertical ou carousel accessible.

Navigation devient menu mobile.

Ne jamais simplement réduire le desktop jusqu’à devenir illisible.

⸻

20. DESIGN TOKENS

Centraliser les tokens.

Ne pas disperser des valeurs arbitraires dans tous les composants.

Prévoir au minimum :

* brand-primary
* brand-primary-hover
* brand-dark
* brand-light
* background
* surface
* text-primary
* text-secondary
* border
* success
* warning
* danger

Même principe pour :

* spacing ;
* radius ;
* shadows ;
* typography ;
* breakpoints.

Si des tokens JAAMA officiels existent déjà dans le repository, ils prévalent.

Ne pas créer un deuxième design system parallèle.

23. ACCESSIBILITÉ

Le respect visuel de la référence ne justifie jamais une mauvaise accessibilité.

Garantir :

* HTML sémantique ;
* navigation clavier ;
* focus visible ;
* contraste suffisant ;
* alt pertinents ;
* boutons réellement interactifs ;
* FAQ accessible ;
* responsive sans overflow horizontal ;
* tailles tactiles suffisantes.

⸻

24. PERFORMANCE

La landing page doit rester rapide.

Éviter :

* dépendances lourdes uniquement pour un petit effet ;
* images non optimisées ;
* animations permanentes coûteuses ;
* JavaScript client inutile ;
* composants client lorsque le rendu serveur suffit.

Optimiser les images et charger intelligemment les éléments non critiques.

⸻

25. INTERDICTIONS TECHNIQUES

Ne jamais :

* mettre toute la landing page dans un seul fichier gigantesque ;
* dupliquer les mêmes styles partout ;
* coder les données métier directement dans des composants lorsque leur réutilisation justifie une configuration ;
* utiliser any pour contourner TypeScript ;
* désactiver ESLint pour faire passer du code incorrect ;
* introduire une dépendance majeure sans justification ;
* casser l’architecture du repository ;
* mettre de la logique backend dans le frontend ;
* accéder directement à PostgreSQL depuis le Web ;
* créer des endpoints backend uniquement pour faciliter une animation visuelle ;
* commencer une autre feature métier pendant l’implémentation de la landing page.

⸻

27. PIXEL-FIDELITY RULE

Pour cette landing page, une implémentation fonctionnelle mais visuellement éloignée est considérée comme INCOMPLÈTE.

Le critère de réussite n’est pas :

« La page ressemble globalement à une landing page JAAMA. »

Le critère est :

« Une personne comparant la référence officielle et l’implémentation reconnaît immédiatement la même composition, la même identité, la même hiérarchie et des proportions très proches. »

Chercher une haute fidélité visuelle, sans sacrifier responsive, accessibilité ou qualité du code.
